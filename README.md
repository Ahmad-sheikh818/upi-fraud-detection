# UPI Fraud Detection — Anomaly Detection on Synthetic Transactions

An end-to-end fraud analytics project: generate 10,000 realistic synthetic UPI
transactions (with labelled fraud), detect fraud with three complementary
methods — IQR outlier detection, Isolation Forest, and time-series anomaly
detection — and evaluate each one against the ground-truth labels.

🎬 [Watch the 60-second project walkthrough on LinkedIn](https://www.linkedin.com/feed/update/urn:li:ugcPost:7509678986302775296)

## Problem statement

UPI fraud in India follows recognisable patterns: odd-hour high-value transfers,
round-number amounts, high-velocity bursts from a single account, and large
payments from new/untrusted devices. The goal is to build detectors for these
patterns and measure how well simple statistical rules, unsupervised ML, and
time-series monitoring each perform.

## Why, how, what

**Why** — UPI fraud losses keep growing, and static blocklists can't keep up:
fraudsters change patterns faster than analysts can write rules. A layered
approach — cheap statistical tripwires plus unsupervised ML plus time-based
monitoring — catches more fraud with fewer analyst hours.

**How** — (1) Generate 10,000 labelled synthetic transactions with four
realistic fraud patterns. (2) Run three detectors at three levels: single
transaction (IQR), transaction + sender context (Isolation Forest), hourly
aggregates (time-series z-score). (3) Score each against ground truth with
precision / recall / F1. (4) Visualise and document.

**What** — a reproducible fraud-detection benchmark: labelled dataset, three
working detectors with honestly measured trade-offs, four charts, and a
Power BI dashboard guide.

## Analytics type

| Type | How this project uses it |
|---|---|
| **Predictive** (primary) | Isolation Forest predicts which transactions are fraudulent — the core value: flag fraud *before* money moves. |
| **Prescriptive** | Flags drive actions: block or step-up-auth on high-confidence hits, analyst review queue from the IQR tripwire, "when to look" radar from time-series. |
| **Diagnostic** | Fraud-by-hour and pattern-mix analysis explain *why* fraud happens when and how it does (e.g. 72% fraud rate at 4am). |
| **Descriptive** | Distribution and time-series charts describe *what* the transaction landscape looks like. |

## Dataset

`data/upi_transactions.csv` — 10,000 transactions over 14 days
(2026-09-01 to 2026-09-14), generated by `data/generate_upi_data.py`
(seed = 42, fully reproducible).

| Column | Description |
|---|---|
| txn_id | Unique transaction id |
| timestamp | Date and time of the transaction |
| sender_id / receiver_id | Payer and payee ids |
| amount | Transaction amount (INR) |
| merchant_category | Grocery, Food & Dining, Travel, … (10 categories) |
| device_type | Android / iOS / New Device |
| city | 12 Indian cities |
| hour_of_day | Hour extracted from timestamp |
| is_fraud | Ground-truth label (1 = fraud) |
| fraud_pattern | Fraud subtype (empty for legitimate txns) |

**Fraud mix (250 transactions, 2.50% of total):**

| Pattern | Count | Description |
|---|---|---|
| odd_hour_high_amount | 72 | High-value txn between 12am–5am |
| velocity_burst | 67 | One sender, many txns within ~30 minutes |
| round_number | 66 | Suspiciously round amounts (₹10k, ₹50k, ₹1L, …) |
| new_device_high | 45 | High amount from a new/untrusted device |

> All data is synthetic. No real users, accounts, or money are involved.

## Approach

1. **Generate** labelled data with realistic legitimate behaviour (log-normal
   amounts, daytime activity peaks) plus the four fraud patterns above.
2. **Detect** with three independent methods, each operating at a different
   level: single transaction (IQR), transaction + sender context
   (Isolation Forest), hourly aggregates (time-series z-score).
3. **Evaluate** precision / recall / F1 of each method against the labels.
4. **Visualise** the findings (charts in `images/`, Power BI guide in
   `powerbi/`).

## Methods

**A. IQR on amounts** — flags transactions above Q3 + 1.5 × IQR
(Q1 = ₹175, Q3 = ₹757, upper fence = ₹1,629). Simple, explainable, no training.

**B. Isolation Forest** — unsupervised ML on engineered features: log amount,
cyclical hour encoding (sin/cos), sender transaction count, sender total amount,
plus one-hot merchant category / device / city. `contamination` set to the
observed fraud rate (0.025), 200 trees.

**C. Time-series z-score** — hourly amount totals compared against the same
hour-of-day baseline across the 14 days; hours with |z| > 3 are flagged and
every transaction inside them is marked suspicious.

## Results

All numbers below are the actual output of `python/fraud_detection.py`
(run on 2026-09-26):

| Method | Flagged | Precision | Recall | F1 |
|---|---|---|---|---|
| A: IQR (amounts) | 941 | 0.255 | 0.960 | 0.403 |
| B: Isolation Forest | 250 | 0.392 | 0.392 | 0.392 |
| C: Time-series z-score | 207 | 0.072 | 0.060 | 0.066 |

**What the numbers mean:**
- **IQR** catches almost every fraud (recall 0.96) but cries wolf — 941 flags
  for 250 real frauds. Great as a first-pass tripwire, too noisy alone.
- **Isolation Forest** is the most balanced: it flagged exactly the 250 most
  suspicious transactions and got 98 of them right. Best single method here.
- **Time-series detection** works at hour granularity, so it is coarse by
  design: 6 anomalous hours flagged, and most transactions inside them are
  legitimate. Useful as an early-warning radar, not a final verdict — it tells
  analysts *when* to look, then transaction-level methods take over.

## Tech stack

Python 3.12 · pandas · NumPy · scikit-learn (Isolation Forest) · matplotlib ·
Power BI (dashboard guide included)

## How to run

```bash
# 1. Install dependencies
pip install -r requirements.txt

# 2. Generate the dataset (10,000 rows -> data/upi_transactions.csv)
cd data
python3 generate_upi_data.py

# 3. Run all three detectors, print metrics, save charts to images/
cd ../python
python3 fraud_detection.py
```
